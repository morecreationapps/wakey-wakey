# Implementation notes

The app uses Expo SDK 57, React Native 0.86, React 19.2, TypeScript 6, Expo SQLite/Notifications and the Temporal polyfill. Exact package versions are recorded in the lockfile. This repository contains generic examples and synthetic test data; a public build starts with an empty rota.

## Data and planning

Planner snapshots are scoped to the verified user's Auth UUID and synchronise with Supabase Postgres through ownership-checked RPCs. The server requires a verified password session and compares snapshot revisions before writing. An account-specific cache retains pending device changes; a conflicting newer server revision is reported rather than overwritten. Browser cache storage uses localStorage and native cache storage uses ordinary SQLite. Corrupt snapshots and unsupported future schema versions are retained and reported. A general future-schema migration framework is not implemented. Undo retains 12 recent in-memory revisions and does not survive restart.

Legacy schema-1 storage remains separate from account caches. A trusted server reservation and verified administrator binding authorise a one-time import of the exact recovered bytes; normal new accounts cannot read or inherit those records. See [the authentication backend guide](auth-backend.md) for the digest checks, before/after verification, idempotent reruns and retained private backup.

Work times are recorded in an explicit work timezone. Temporal converts them to exact instants for elapsed calculations and DST checks. Nonexistent local times are rejected; repeated times require an explicit earlier/later choice. A single choice currently applies to both duty boundaries, so a duty cannot distinguish earlier and later copies of identical repeated clock endpoints.

The planner subtracts arrival buffer and the entered outbound upper travel estimate from a shift start, then subtracts essential preparation. It derives separate preparation, departure, arrival, bedtime, target sleep start and wind-down events. A combined routine is counted once; overlapping named activities require review. Return travel and recovery are separate inputs. Suggested durations and unconfirmed inputs remain provisional.

For example, a 06:00 shift, 10-minute arrival buffer, 20-minute journey and 30-minute preparation routine imply 05:00 preparation, 05:30 departure and 05:50 arrival. A seven-hour target gives 22:00 target sleep start; 30-minute latency gives 21:30 bedtime; a full 60-minute wind-down starts at 20:30. These are synthetic arithmetic examples, not measured sleep.

Sleep setup and Settings → Sleep share four optional preferences: bedtime and wake-up before an early shift, and bedtime and wake-up before a late shift. Bedtime is on the previous calendar date in the selected duty's recorded timezone; wake-up is on that duty's date. These pairs take precedence for their matching duty and drive editable task-entry suggestions and automatic preparation tasks. They remain distinct from ordinary rest-day sleep and post-work recovery preferences. Older schema-1 snapshots may omit the new keys and are read without injecting values or rewriting their bytes; new accounts start with blank preferences. No backend schema or permission changes are required.

Actual finish supersedes a planned overtime extension for recovery; overtime is not added twice. Requested holiday never establishes free time or approved return-to-work guidance. Shift changes and confirmed holiday returns produce transparent review advice. A 30-minute gradual-adjustment heuristic is not a measured circadian model or clinical advice. Exact steps are withheld when recovery preferences are unknown, and specialised night-shift coaching remains unavailable.

Task placement is deterministic and greedy. It reserves fixed commitments, work/travel, essential preparation, full planned sleep/recovery and protected rest-day time before fitting tasks. It may miss an alternative feasible arrangement; users can revise or lock commitments. Its near-term horizon is 14 days. The rest-day personal-time reserve currently starts at 16:00; a fixed commitment can express another time. Completed/skipped recurring occurrences are separate from the series.

Today separates two stages. **Shift transition** anchors to the previous calendar date in the same recorded timezone as the next duty shown in **Prepare for my next shift**. It places linked or relevant saved tasks before the protected bedtime routine, with the meal before the bedtime shower and the full wind-down before bedtime. Matching saved wind-down or sleep activities replace generated routine rows. **Shift Plan** uses the existing `planShift` result, including its sleep, wake, preparation, departure, arrival and work events. Counted missing-input notices and settings actions are hidden only in these two Today panels; unresolved task conflicts remain visible and settings are available elsewhere.

Recognised task names receive editable duration and start suggestions derived from that duty, the current settings and existing commitments. Suggestions update only untouched draft fields. An optional `preparationAutoStart` flag distinguishes a suggested start that can reflow from a deliberately chosen or locked time. Completing or skipping a one-off automatic task records its latest displayed placement; recurring occurrence states do not alter the series. Optional deadline, window and travel controls remain blank when unused. Their `omittedFields` metadata preserves that presentation while canonical scheduling bounds remain valid for existing account snapshots and backup validation. These optional fields require no database migration.

## Platform behaviour

Reminders require opt-in, permission and confirmed setup. Automatic refresh follows a successfully saved revision. The active account owns its reminder schedule; logout or account switching clears that owner and cancels app reminders. Stable identifiers and cancellation before replacement prevent duplicate app reminders. A rolling queue considers 14 days and caps at 60 events; reopening or foregrounding renews it. Ordinary notifications remain subject to OS permissions, Focus/sound/battery behaviour. Verified OS alarms, critical alerts, exact-alarm guarantees and indefinite background refill are not implemented. Web reminders report unsupported status.

Text/CSV import requires a reviewed preview, validates dates/overlap/duplicates and does not execute input. Calendar exports omit private notes and sleep records by default; complete JSON backups contain them. Restore validates schema 1 before replacing the current account's planner. CSV formula escaping is an initial-export mitigation, not a universal guarantee after spreadsheet re-saving. Planner caches and backups are not encrypted. Native session credentials use secure storage; browser session credentials use localStorage.

## Authentication

Supabase Auth supplies email-and-password accounts, confirmation codes and password recovery. The app exposes no guest, social, phone or magic-link sign-in. Codes are purpose-specific and do not grant planner access. Confirmation is followed by password login; recovery permits a password update, then signs out and returns to normal password login. A restoration screen hides protected views while the provider checks the session. Logout unmounts the current account's views and clears its session without deleting planner records.

Password drafts and codes remain in memory. Password values are not trimmed or truncated; new passwords require at least 12 characters and matching confirmation. Inputs carry email, current/new-password and one-time-code autofill hints. Shared theme variables, original transparent logo assets, rounded cards, visible focus treatments, loading notices and keyboard-aware scrolling are reused. The exact orange/white palette retains the contrast limits recorded in [the brand verification record](brand-theme-verification.md); no full accessibility claim is made.

The frontend remains unavailable when account/email configuration is incomplete. It does not show a simulated successful email send. Configuration and actual delivery checks are separate from source checks and local Auth-provider fixtures; the backend guide records the remaining operator steps.

## Development preview and remaining work

The browser frontend is statically hosted, with a separate Supabase authentication/data backend and account-specific origin/profile caches. Assets still need to load from the host; there is no service worker for guaranteed offline cold starts. In a running app, a previously validated and unexpired password session can retain access to its own cache during network failure. A cold offline start does not trust a cache as proof of authentication. There are no analytics calls. GitHub Pages project paths share the host's browser origin, so they do not provide independent storage security boundaries.

Before a mobile release, verify standalone iOS/Android offline restart, actual notification delivery/denial/cancellation, native file sharing and backup restore on physical devices. Complete screen-reader, keyboard, large-text and device accessibility checks. Sleep guidance and transition wording require qualified specialist review; the educational source links do not establish clinical validation or fitness for duty.

Photo/PDF/OCR input is deferred until it has an editable uncertainty-aware preview and explicit confirmation. Other later work includes calendar synchronisation, widgets, opt-in sharing, wearable integration, travel disruption sources, diary trends and specialist night-shift coaching.
