2. Enable email signup and email confirmation. Disable anonymous, phone, social, passkey, Web3 and third-party OAuth sign-in providers. Keep manual account linking off. The app exposes only email-and-password signup/login and purpose-specific verification/recovery screens.
3. Set the minimum password length to **12**. Passwords are passed unchanged; pasting and password managers must remain supported. Password-recovery sessions may update the password, then must sign out and log in with that new password.
4. Configure email codes to **8 digits**, expiry **600 seconds**, and resend/reset frequency **60 seconds**. Use `supabase/templates/confirmation.html` for Confirm Signup and `supabase/templates/recovery.html` for Reset Password. Both use `{{ .Token }}` and omit confirmation/magic-login links. Do not configure these templates until the matching expiry is set.
5. Configure a real custom SMTP provider with its verified sender address/domain, SMTP hostname, port, user and password. Store credentials in Supabase's server configuration only. Do not put SMTP passwords, service-role keys, database passwords or management tokens in Expo variables, GitHub source, app snapshots or logs.
6. Apply and read back server rate-limit settings. The CLI configuration now matches the observed hosted quotas: **30 signup/sign-in requests per 5 minutes per IP**, **30 token-verification requests per 5 minutes per IP**, **150 refreshes per 5 minutes per IP** and **30 combined auth email sends per hour per project**. Supabase uses a token bucket: brief bursts can occur; these are not a promise of an account lock after a particular number of guesses. Auth returns 429 when limits are exceeded. Enable a supported CAPTCHA if required by observed abuse; no CAPTCHA secret belongs in the public bundle.
7. The hosted Site URL is `https://morecreationapps.github.io/wakey-wakey/`, and the redirect allowlist remains empty for these code-only flows. Keep automatic URL session detection disabled in the client; confirmation/recovery codes are entered in their intended forms. 8. Supply only the project URL and **publishable** key to the frontend. Keep the application's real-email readiness switch false until sender verification, code templates, limits and actual delivery are verified. Request acceptance is not proof an email arrived.

## Account data contract

| RPC                        | Parameters                                         | Result                                                       |
| -------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| `planner_load`             | none                                               | `{ payload: string \| null, revision: number }`              |
| `planner_save`             | `p_payload: string`, `p_expected_revision: bigint` | `{ payload: string, revision: number }`                      |
| `planner_migration_status` | none                                               | `{ eligible: boolean, completed: boolean, digest?: string }` |
| `planner_migrate_legacy`   | `p_payload: string`, `p_digest: string`            | `{ payload: string, revision: number, digest: string }`      |

All account IDs come from `auth.uid()`. None of these methods accepts a caller-supplied owner ID. Every call requires a currently verified, non-anonymous Auth user, a password-only signed AMR, and a live matching `auth.sessions` record; expired server sessions, deleted/banned users and third-party OAuth clients are also denied. Verification-code, recovery, magic-link, social and mixed recovery/password AMRs cannot read or write app data. A normal password login after confirmation/reset establishes the permitted session.

`public.planner_snapshots` is one raw JSON-text snapshot per account, retaining settings, templates, rota entries, repeating patterns, tasks and sleep logs. RLS permits only the verified password user's own read. Direct client INSERT/UPDATE/DELETE is revoked; mutation occurs through guarded private functions called by public `SECURITY INVOKER` wrappers. Private elevated functions have an empty search path, explicit Auth checks and narrowly granted execute privileges. The app role cannot read Auth tables, administrator bindings, migration reservations or rate counters.

Saves validate schema-1 field types, bounds, dates/times, record IDs and relevant cross-record relationships on the server, while retaining the exact original payload bytes. An account advisory lock and expected revision compare-and-swap prevent a stale device from overwriting newer data. A server limit allows at most 120 successful writes per minute per account. A conflict produces SQLSTATE `40001`; permission failures use `42501`, validation failures `22023`, and migration state errors `55000`.

## Trusted administrator setup and migration

The approved administrator email is an operator input, never a browser-authorisation rule. No first-user rule, client metadata or frontend email comparison grants privileges. The administrator role is stored privately against a verified Auth UUID and **does not grant access to anyone else's records**.

Before any authentication/storage change, recover the exact development snapshot from its current `http://localhost:8081/` origin and preserve its storage backup. Retain the original raw JSON-text bytes in a private backup file, record SHA-256 and collection counts, and validate the existing schema without replacing missing values. Never commit the personal backup or reconstruct it from examples. Do not change the development origin or reset its storage before recovery.

Run `scripts/prepare-admin.mjs` only from a trusted operator machine with a privileged PostgreSQL connection. It uses `psql` and takes credentials through environment variables rather than command-line arguments. It prints only receipt UUID/digest/status, never the password, connection URL or snapshot. It neither creates a user nor sets/resets any password.

1. Privately set `SUPABASE_DB_URL`, `ADMIN_EMAIL`, `ADMIN_BACKUP_FILE` and the independently recorded `ADMIN_BACKUP_SHA256`. Set `ADMIN_SETUP_ACK=reviewed-account-and-backup` after confirming the approved target and exact backup.
2. **Before administrator signup/first app login**, set `ADMIN_SETUP_ACTION=reserve` and run `node scripts/prepare-admin.mjs`. This establishes a server-only reservation for the approved email and digest. It grants no administrator role. If that verified user reaches the app before binding, load/status/save return `42501` with “Administrator setup is awaiting trusted migration approval.” Defaults cannot overwrite the recovered settings in that window.
3. The owner creates their email-and-password account themselves and verifies email ownership with the real confirmation code. They choose a new password securely. If an account already exists, use its normal secure recovery flow with the owner's participation; never overwrite it or reset its password automatically.
4. Obtain the already verified account UUID from trusted Supabase Auth administration. Privately set `ADMIN_USER_ID` and `ADMIN_SETUP_ACTION=bind`, then run the same tool. The server checks the UUID's Auth email, verification state and password identity against the explicit approved operator input and pre-existing reservation. A different backup, an unverified identity, a wrong account or existing cloud settings is refused. Rerunning the same binding is idempotent.
5. Log in normally with the verified email and password. The client can see only its bound migration eligibility. Submit the recovered raw payload with its trusted digest to `planner_migrate_legacy`. The transaction checks the digest, validates the full snapshot, requires an absent destination, inserts once, reads back and compares exact UTF-8 bytes and SHA-256, and only then records migration completion. Any failure rolls back both insert and receipt.
6. The client also compares the returned/read-back values with the saved original before declaring success. Completed settings skip onboarding. Keep the original backup until migration verification is documented; this tool never deletes it.
7. Rerunning a completed migration returns the account's **current** snapshot and original migration digest. It does not reinsert, duplicate or replace newer records. This matters after the administrator edits settings on another device.

If the original development data, project provisioning, SMTP sender or administrator verification is unavailable, report that specific state. Prepared SQL, passing fixture tests, a request accepted by Auth, and a migration grant are separate from live deployment, mailbox delivery, owner verification and actual personal-data migration.

## Planner version conflict recovery — 8 October 2026

A successful password session can reach the planner and still be blocked by a dirty device cache based on an older account revision. Previously this view offered only Retry and Log out, without a way to resolve the different snapshots. Authentication must remain intact while this data conflict is reviewed.

The frontend now reads both versions through the existing authenticated account endpoints, validates ownership and migration receipts, and displays version numbers and record totals. The user can download either complete JSON backup and explicitly choose to open the saved account version. It does not automatically merge or publish the pending device changes.

Before changing the active device copy, recovery preserves both exact original payloads (and the complete pending cache envelope) under immutable account-scoped SHA-256 addresses. It verifies these copies and their latest-recovery index by reading them back, then checks the backend and active device version again. Changed reviews, owner mismatches, migration/rollback conditions, storage failures and backup verification failures refuse adoption. Opening the account copy performs no backend save. Preserved copies remain downloadable from Settings after a reload. These copies live in the same local storage as the planner and are lost if the user clears that storage; separate downloads provide an additional copy.

A planner loaded or recovered from storage starts fresh header feedback and undo history. It no longer saves an identical snapshot merely because the app opened. Actual edits keep the existing compare-and-swap save behaviour. Refresh attempts normal loading first, so a conflict resolved elsewhere can reopen without requiring logout.

No database schema, account role, verification requirement or authentication permission changes are needed for this recovery flow.
